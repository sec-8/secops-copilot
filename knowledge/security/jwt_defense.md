# JWT 安全防御

> 覆盖变体：`alg=none` 绕过、弱密钥爆破、`kid` 路径注入、过期未校验。  
> 防御同源：强签名算法（RS256/PS256）+ 密钥强度保障 + `iss`/`aud`/`exp` 完整校验。

## 漏洞成因

JWT（JSON Web Token）安全问题的根本成因在于：应用程序对 JWT 的签名验证环节存在配置缺陷或实现漏洞，攻击者可利用这些缺陷伪造合法令牌或绕过校验逻辑。典型攻击路径包括：将签名算法降级为 `none` 绕过验证、通过弱密钥暴力破解 HS256 签名、利用 `kid`（Key ID）头参数进行路径遍历读取服务器文件、或使用已过期令牌重复请求。核心问题是服务端对令牌的完整性和有效性验证不严格，过度信任客户端提供的令牌内容。

## JWT 安全检测方法

检测目标在于发现 JWT 解析和验证环节的配置缺陷：

- **alg=none 检测**：将令牌头中的 `alg` 字段修改为 `none`，移除签名部分，提交给服务端，观察是否被接受。若服务端接受 `alg=none` 令牌，则存在绕过漏洞。
- **弱密钥爆破检测**：针对 HS256 签名的 JWT，使用常用弱密钥字典（如 `secret`、`password`、`123456`）尝试暴力破解签名密钥，验证服务端是否使用了弱密钥。
- **kid 注入检测**：检查令牌头中的 `kid` 参数是否被服务端用于读取文件系统（如 `../../../../etc/passwd`）或数据库查询。通过构造恶意 `kid` 值，观察服务端异常或响应差异判断是否存在注入。
- **过期校验检测**：将过期令牌（`exp` 已超时）提交给服务端，观察是否被拒绝。若服务端未校验 `exp` 或允许长时间过期令牌通过，则存在风险。

关键原则：检测需覆盖 JWT 的完整生命周期——签名验证、声明校验、有效期校验，任何环节的缺失均为漏洞。

## 防御机制：算法锁定 + 密钥强化 + 声明完整校验（三层）

### 第一层：强签名算法与密钥管理（核心防线）

- **算法强制白名单**：服务端仅允许使用强非对称签名算法（RS256、PS256、ES256）或强对称算法（HS256 配高熵密钥）。**必须明确拒绝 `alg=none`**，并在解析库中禁用该选项（如 JJWT 的 `setVerifySignatureRequired(true)`）。
- **密钥强度保障**：若使用 HS256，密钥必须为高熵随机字符串（建议 ≥ 256 位，即 32 字节以上），由环境变量或密钥管理服务注入，**不可硬编码在代码中或使用简单字符串**（如 `secret`）。
- **定期轮换密钥**：对称密钥和非对称密钥对应定期轮换（如每季度），并建立密钥版本管理机制，确保旧令牌在宽限期内仍可验证，过期后彻底失效。
- **kid 安全解析**：若使用 `kid` 参数选择密钥，必须对 `kid` 值做严格校验，仅允许预定义的标识符（如 `key-1`、`key-2`），禁止直接拼入文件路径或数据库查询，杜绝路径遍历和注入攻击。

### 第二层：完整声明校验（验证令牌可信度）

在签名验证通过后，必须对 JWT Payload 中的标准声明逐一校验：

- **exp（过期时间）**：校验当前时间是否在 `exp` 之前，拒绝已过期的令牌。**必须做校验，不可跳过**。
- **nbf（生效时间）**：校验当前时间是否在 `nbf` 之后，拒绝尚未生效的令牌（防重放）。
- **iat（签发时间）**：可选校验，与当前时间差不应超过允许的最大偏移（防时钟偏差）。
- **iss（签发者）**：校验 `iss` 是否与预定义的可信签发者列表匹配，拒绝来自未知签发者的令牌。
- **aud（受众）**：校验 `aud` 是否包含当前服务端的标识，防止令牌被用于非预期的资源访问。

**实现关键**：声明校验应在统一拦截器或过滤器层完成，避免业务代码分散实现导致遗漏。

### 第三层：令牌生命周期管控（最小化暴露窗口）

- **短有效期设计**：根据业务敏感程度设置合理的有效期（如 Access Token 15~60 分钟，Refresh Token 7 天），缩短攻击者可利用的时间窗口。
- **Refresh Token 机制**：使用短生命周期 Access Token 配合 Refresh Token 换取新令牌，Refresh Token 需存储服务端并与用户绑定，支持撤销。
- **主动撤销能力**：提供令牌黑名单机制（如基于 Redis 的 JTI 黑名单），用户注销、修改密码或检测到异常登录时，立即使当前令牌失效。
- **单令牌限制**：限制同一用户同时有效的令牌数量（如最多 5 个），超出时最早签发的令牌自动失效，减少劫持影响面。

## 纵深防御（辅助层）

- **令牌绑定客户端**：将 JWT 与客户端特征（如 IP 段、User-Agent 哈希）绑定，降低令牌被劫持后异地使用的风险。注意 IP 动态变化场景需适度放宽。
- **传输安全强制**：JWT 必须通过 HTTPS 传输，杜绝明文网络中令牌被截获，同时设置 Cookie 的 `Secure` 和 `HttpOnly` 属性（若使用 Cookie 存储）。
- **日志审计**：记录所有 JWT 验证失败的尝试（签名失败、过期、声明不匹配），监控异常激增模式，及时发现爆破或绕过尝试。
- **使用成熟库**：依赖经过安全审计的 JWT 库（如 Java 的 JJWT、Python 的 PyJWT、Node.js 的 jsonwebtoken），避免自行实现 Base64Url 编解码和签名逻辑。

## 安全金律

- **永远不信任 `alg=none`**：在 JWT 解析库中显式禁用 `none` 算法，服务端拒绝任何未签名的令牌。
- **密钥是安全的基石**：HS256 密钥必须高熵且保密存储，RS256 私钥严禁硬编码，定期轮换并建立版本管理。
- **声明校验一个都不能少**：`exp`、`iss`、`aud` 为必检项，缺失或无效则直接拒绝，不可放行。
- **短令牌 + 可撤销**：Access Token 有效期不超过 1 小时，并提供服务端撤销能力，不能依赖客户端主动销毁。
- **kid 不能直接用于路径查询**：`kid` 必须严格白名单校验，防止路径遍历和注入攻击，避免将其拼入文件路径或 SQL 语句。
