# IDOR / 越权访问防御

> 覆盖变体：水平越权（同角色访问他人资源）、垂直越权（低权限调用高权限功能）、平行越权（不同租户间交叉访问）。  
> 防御同源：服务端强制鉴权 + 间接对象引用 + 权限缓存实时校验。

## 漏洞成因

越权访问的根本成因在于：应用程序依赖前端传入的资源标识符（如 URL 中的 `orderId=123`）来定位数据，但服务端未对当前用户是否拥有该资源的访问权限做校验。攻击者通过遍历或猜测资源 ID、修改请求参数中的用户编号或角色字段，可访问本不属于自己的数据或执行越级操作。其本质是“资源归属”与“用户身份”之间的绑定关系未被服务端严格验证，仅靠前端隐藏或灰显按钮无法防御。

## 防御机制：资源归属校验 + 间接引用 + 角色管控（三层）

### 第一层：服务端强制权限校验（核心防线）

在处理任何涉及资源的请求时，服务端必须校验当前用户对该资源是否拥有访问权限：

- **水平越权校验**：在查询、修改、删除资源时，首先通过当前会话中的用户标识（如 `userId`）查询该资源是否属于当前用户。比对方式应使用服务端存储的资源归属字段（如 `orders.user_id = current_user_id`），而非信任客户端传入的 `userId` 参数。
- **垂直越权校验**：在调用 API 前，通过角色权限矩阵（RBAC）校验当前用户是否具备该操作所需的最小权限等级。例如，普通用户调用管理员接口 `POST /api/admin/users` 时，服务端须验证其角色是否包含 `ADMIN` 权限。
- **校验时机**：权限校验必须在数据查询或操作之前执行，不可将数据先取出再判断（防止通过异常回显探测数据是否存在）。

### 第二层：间接对象引用（隐藏真实标识）

避免在请求中直接暴露数据库自增 ID 或业务主键：

- **使用映射令牌**：用服务端生成的随机 UUID 或哈希字符串作为资源的外部引用标识（如 `/orders/{uuid}`），服务端通过映射表解析 UUID 得到真实资源 ID，再执行归属校验。攻击者无法通过遍历连续数字获取其他用户资源。
- **用户级映射隔离**：每个用户的映射表相互独立，同一 UUID 在不同用户上下文中可指向不同资源，进一步增强隐蔽性。
- **映射有效期**：对临时性资源引用（如分享链接）可设置过期时间，降低泄露后的影响窗口。

**注意**：间接引用不能替代权限校验，仅作为隐藏目标的手段，核心安全仍依赖第一层的归属验证。

### 第三层：多层权限模型（深度校验）

对于复杂业务场景，采用分层权限模型：

- **租户隔离**：在多租户系统中，所有查询必须携带租户标识（如 `tenant_id`），服务端确保当前用户所属租户与资源租户一致。
- **资源级权限**：对敏感数据（如订单、文档）可使用 ACL（访问控制列表），记录每个用户或角色对特定资源的操作权限（读/写/删除）。
- **上下文权限**：某些操作依赖业务状态（如“只有订单创建者可取消订单”），需在业务逻辑层额外校验资源状态与用户身份的匹配关系。

## 纵深防御（辅助层）

- **API 级访问控制**：统一通过拦截器或 AOP 切面实现权限校验，避免业务代码分散实现导致遗漏。所有需要认证的接口默认拒绝，仅通过注解或配置显式开放。
- **数据层过滤**：在 ORM 查询中自动追加当前用户的归属条件（如 `WHERE user_id = {currentUserId}`），即使上层校验遗漏，数据层仍可限制结果集范围。
- **审计日志**：记录所有越权访问尝试（403 响应），包括请求参数、用户身份、目标资源，定期分析异常模式以发现攻击行为。
- **敏感参数去客户端化**：涉及用户身份、角色、租户等关键字段，不应出现在前端请求体中，而是由服务端从会话或令牌中提取，从根本上杜绝参数篡改。

## 安全金律

- **永不信任前端传入的身份标识**：`userId`、`role`、`tenantId` 等关键字段必须从服务端会话中获取，而非请求参数。
- **权限校验是服务端必选项**：无论前端是否做按钮级权限控制，服务端必须独立校验每个操作的权限，前端控制仅用于提升用户体验。
- **暴露的资源 ID 必须为非连续可预测**：使用 UUID 或哈希作为外部标识，避免攻击者通过遍历 ID 批量获取数据。
- **校验必须先于数据操作**：权限判断在数据查询或更新之前完成，不可依赖先查询后判断再返回的模式。
- **默认拒绝原则**：所有接口默认无权限，仅通过显式配置授权，避免新增接口因疏忽而遗漏校验。
