# XSS 防御

> 覆盖变体：存储型 XSS、反射型 XSS、DOM 型 XSS。  
> 防御同源：上下文感知输出编码 + CSP 浏览器策略 + 输入校验。

## 漏洞成因

XSS（跨站脚本）的根本成因在于：应用程序将用户可控的数据未经过滤或编码直接输出到 HTML 页面中，导致攻击者注入的恶意脚本在受害者浏览器中执行。三种类型的共同本质是“不可信数据进入 DOM 执行上下文”，区别仅在于注入路径：

- **存储型**：恶意数据持久化在服务端数据库，每次访问页面时被加载执行。
- **反射型**：恶意数据通过 URL 参数等即时输入，经服务端反射回页面执行。
- **DOM 型**：恶意数据在客户端通过 JavaScript 操作 DOM 时被直接写入页面执行，完全不经过服务端。

无论哪种类型，防御核心都是：**在数据进入执行上下文之前，确保其仅作为文本而非代码被解析**。

## 防御机制：编码层精准 + 浏览器层兜底（三层）

### 第一层：上下文感知输出编码（核心防线）

输出编码的核心原则是：针对数据最终出现的上下文，采用对应的编码规则，而非一刀切的 HTML 实体编码。

- **HTML 上下文**（数据出现在标签内容中，如 `<div>{{data}}</div>`）：进行 HTML 实体编码，将 `<` `>` `&` `"` `'` `/` 等字符转换为 `&lt;` `&gt;` `&amp;` 等实体，使浏览器将其解析为普通文本而非标签或属性。
- **HTML 属性上下文**（数据出现在标签属性值中，如 `<input value="{{data}}">`）：除 HTML 实体编码外，必须对引号进行编码，防止攻击者提前闭合属性注入新事件（如 `onerror`）。建议属性值用引号包裹，并对引号做实体编码。
- **JavaScript 上下文**（数据出现在 `<script>` 标签或事件处理器中，如 `var x = "{{data}}"`）：使用 Unicode 转义（`\u003c`）或 JSON 序列化，确保数据被当作字符串字面量而非代码执行。仅靠 HTML 实体编码在此无效，因为 JS 引擎会先解码实体再执行。
- **URL 上下文**（数据出现在链接 URL 中，如 `<a href="{{data}}">`）：进行 URL 百分号编码，且严格限制协议白名单（仅允许 `http/https`，禁用 `javascript:` 伪协议）。

**推荐方案**：使用成熟的模板引擎（如 Spring 的 Thymeleaf、Vue/React 的自动转义）或 OWASP Java Encoder 等库，由框架自动识别上下文并采用对应编码规则，避免自行实现编码逻辑。

### 第二层：输入校验与过滤（辅助增强）

作为编码的补充，对输入数据做适度校验和过滤：

- **富文本场景**（用户需提交 HTML 内容，如博客正文）：不能整体编码，应使用严格的 HTML 净化器（如 OWASP Java HTML Sanitizer、DOMPurify），基于白名单过滤保留安全标签（如 `<p>` `<b>` `<img>`）及其属性，剥离所有危险标签（`<script>` `<iframe>`）和事件属性（`onerror` `onload`）。
- **格式校验**：对邮箱、URL、数字等有明确格式要求的字段，使用正则验证其格式合法性后再存入。
- **字符长度限制**：合理限制输入长度，增大攻击构造难度，但仅作辅助。

**注意**：输入过滤不可替代输出编码，因为攻击载荷可能在数据流转中二次变形，且存储型 XSS 依赖的是输出环节而非输入环节。

### 第三层：CSP 浏览器策略（兜底防线）

CSP（内容安全策略）通过 HTTP 响应头或 `<meta>` 标签配置，限制浏览器只加载和执行白名单内的资源，即使页面存在注入点，恶意脚本也无法执行：

- **核心配置**：`Content-Security-Policy: default-src 'self'; script-src 'self'` 限制脚本只能从同源加载，禁止内联脚本和执行 `eval()`。
- **非一次性加固**：如业务必须使用内联脚本，可使用 `nonce`（一次性随机值）或 `hash` 方式授权，避免完全放行 `unsafe-inline`。
- **限制外部资源**：禁止 `http:` 和 `data:` 协议加载脚本，防止恶意第三方脚本注入。

CSP 提供“最后一道闸门”，其有效性依赖策略的严格程度。建议从 `Report-Only` 模式开始测试，逐步收敛到严格策略。

## 纵深防御（辅助层）

- **Cookie 安全属性**：为会话 Cookie 设置 `HttpOnly` 属性，防止 JavaScript 读取 Cookie，从而降低存储型 XSS 盗取会话的风险；设置 `Secure` 和 `SameSite=Strict` 增强传输安全。
- **弃用危险 API**：避免在代码中使用 `document.write`、`eval`、`innerHTML` 等直接插入 HTML 字符串的 API，优先使用 `textContent` 或 `innerText`，或使用框架的模板语法进行安全绑定。
- **框架自带的 XSS 防护**：现代前端框架（React、Vue、Angular）默认对模板插值进行自动转义，应在项目中充分利用该机制，并避免手动禁用（如 `v-html`、`dangerouslySetInnerHTML`）。

## 安全金律

- **编码决策点在于输出**：XSS 防御发生在输出阶段，输入过滤不能取代编码。在任何数据写入 HTML 页面前，必须按其上下文执行对应的编码。
- **区分三种上下文**：HTML 实体编码仅适用于标签内容，JS 上下文必须用 Unicode 转义或 JSON 序列化，URL 上下文须百分号编码。一码通吃是防御失效的常见根源。
- **CSP 是最后防线**：即使编码遗漏，严格 CSP 可阻止脚本执行，但需注意其不能替代编码，而是作为纵深防御的兜底。
- **避免自行实现编码库**：框架和成熟库已经过广泛安全验证，自行实现极易遗漏边界情况（如 JS 中的 `\u` 绕过），应优先依赖标准化方案。
- **不可信数据绝不直接操作 DOM**：禁止使用 `innerHTML`、`document.write` 等危险 API 插入未经过滤的用户数据，使用 `textContent` 或框架安全绑定替代。
