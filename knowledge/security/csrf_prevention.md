# CSRF 防御

> 覆盖变体：GET 型 CSRF、POST 型 CSRF、JSONP 劫持。  
> 防御同源：Anti-CSRF Token（会话绑定）+ SameSite Cookie 属性 + 敏感操作二次验证。

## 漏洞成因

CSRF（跨站请求伪造）的根本成因在于：浏览器在发起跨域请求时会自动携带目标域名的 Cookie（包括会话凭证），而服务端无法区分该请求是用户本人在可信页面主动发起，还是恶意网站通过表单、脚本、图片等自动构造的伪造请求。攻击者利用已登录用户的会话，在用户不知情的情况下以用户身份执行非预期操作（如修改密码、转账、删除数据）。核心问题是“请求来源”与“用户意图”之间缺乏绑定验证。

## CSRF 检测方法

检测目标在于发现未对请求来源和用户意图进行校验的敏感操作接口：

- **GET/ POST 型检测**：构造一个来自第三方域名的表单提交或图片请求，指向目标接口（如 `/api/transfer`），观察是否在未携带额外凭证（如 Token）的情况下成功执行操作。自动化扫描器通过检测敏感接口（如修改、删除、转账）并模拟跨域请求，比对执行结果判断是否存在漏洞。
- **JSONP 劫持检测**：检查响应是否包含 JSONP 回调函数（如 `callback=jsonp`），且未校验回调来源或 Referer，导致恶意页面可通过 `<script>` 标签跨域窃取敏感 JSON 数据。

关键原则：所有涉及状态变更（POST/PUT/DELETE）的接口均为检测重点；对 GET 请求，仅当具有副作用（如删除操作通过 GET 实现）时才纳入检测范围。

## 防御机制：令牌绑定 + 来源校验 + 二次确认（三层）

### 第一层：Anti-CSRF Token（核心防线）

在服务端生成一个不可预测的随机令牌，与当前用户会话绑定，并嵌入到表单或请求头中，提交时服务端校验令牌有效性：

- **生成与绑定**：每个会话生成独立的 CSRF Token（通常为高熵随机字符串），存储在服务端 Session 中，同时下发给前端（可置于 HTML 隐藏字段或 Meta 标签）。
- **请求携带**：前端在提交敏感请求时，从页面或 Cookie 中读取 Token，放入请求头（如 `X-CSRF-Token`）或请求体。**必须确保 Token 不通过 URL 参数传递**（易被 Referer 泄露）。
- **服务端校验**：接收请求后，将客户端提交的 Token 与会话中存储的 Token 比对，不一致则拒绝请求。校验失败不返回敏感信息，统一返回通用错误。
- **双重提交 Cookie 模式**（无状态方案）：服务端生成 Token 并写入 Cookie，前端读取后放入请求头，服务端比对两者是否一致。需注意 Cookie 的 `SameSite` 属性配合使用，且不与 Session 绑定导致 Token 可复用。

**注意**：Token 不可由前端生成，必须服务端下发；Token 必须与会话绑定，单一 Token 不可跨会话复用。

### 第二层：SameSite Cookie 属性（浏览器层兜底）

通过设置 Cookie 的 `SameSite` 属性，限制第三方站点在跨域请求中携带 Cookie：

- **SameSite=Strict**：任何跨域请求均不携带 Cookie，适用于没有第三方嵌入需求的场景，防御效果最强。
- **SameSite=Lax（推荐）**：允许顶级导航（如点击链接跳转）携带 Cookie，但禁止 POST/ PUT/ DELETE 等跨域请求携带，可覆盖绝大多数攻击场景，同时保持用户体验。
- **SameSite=None**：仅当确实需要跨域携带 Cookie 时使用，且必须配合 `Secure` 属性（仅 HTTPS），否则浏览器会拒绝。

**定位**：SameSite 提供浏览器级的默认防御，但不能完全依赖（旧浏览器不支持），须与 Token 配合形成纵深。

### 第三层：敏感操作二次验证（兜底确认）

对高风险操作（修改密码、资金转账、绑定手机、删除账号等），在执行前要求用户主动参与确认：

- **密码重验证**：要求用户再次输入登录密码，服务端验证通过后本次操作才可继续，可阻断所有自动化 CSRF 攻击。
- **验证码/短信验证码**：在操作前发送一次性验证码至用户手机或邮箱，要求输入后执行。该验证码为单次有效、时效性强，攻击者无法跨域获取。
- **生物特征校验**：对极高敏感操作（如支付、授权）可使用指纹/人脸识别。

**定位**：二次验证不直接防御 CSRF，但可确保任何高危险操作背后有用户的主动意图确认，是最后的兜底手段。

## 纵深防御（辅助层）

- **Referer/Origin 校验**：服务端校验请求头中的 `Origin` 或 `Referer` 字段，确保来源域名为白名单内的可信站点。注意 Referer 可能因隐私策略或代理被删除，不可作为唯一依赖。
- **自定义请求头**：在 AJAX 请求中添加自定义头（如 `X-Requested-With: XMLHttpRequest`），现代浏览器会触发 CORS 预检，跨域请求无法自动添加，可阻隔简单的表单型 CSRF。但需配合 CORS 配置，且不适用于 `<form>` 直接提交。
- **敏感操作改用 POST**：严格遵循 REST 语义，所有状态变更操作使用 POST/PUT/DELETE，不使用 GET 执行副作用，消除图片 URL 等方式触发的 GET 型 CSRF。
- **JSONP 禁用与 CORS 收紧**：禁止使用 JSONP 跨域方案（易产生劫持），改用 CORS 并配置严格的 `Access-Control-Allow-Origin` 白名单，不反射 `Origin`。

## 安全金律

- **状态变更操作必须上 Token**：任何 POST/PUT/DELETE 接口，必须校验 CSRF Token，不可遗漏。Token 须与会话绑定且服务端生成。
- **Token 不可通过 URL 传递**：放在请求头或请求体中，防止被 Referer 或浏览器历史记录泄露。
- **SameSite 是浏览器层的有效补充**：推荐设置 `SameSite=Lax`，但不能替代 Token，仅作为纵深的一环。
- **二次验证用于高敏操作**：修改密码、资金转移等操作，强制要求密码或验证码重验，是最后一道闸门。
- **默认拒绝跨域写操作**：服务端应主动校验 Origin/Referer，对来源不明或非白名单域的写请求一律拒绝。
