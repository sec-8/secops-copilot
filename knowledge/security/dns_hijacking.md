# DNS 劫持防御

> 覆盖变体：中间人篡改响应、递归缓存污染、本地 Hosts 篡改、流氓 DNS 服务器。  
> 防御同源：加密传输 + 响应验证 + 可信解析器。

## 漏洞成因

DNS 劫持发生在域名解析过程中，攻击者篡改 DNS 响应、污染递归缓存、劫持请求路由或修改 Hosts 文件，将域名指向恶意 IP。用户最终访问钓鱼站点或中间人代理，导致凭证泄露或数据窃取。根本成因在于 DNS 协议缺乏端到端加密和强验证机制，响应可被伪造。

## 防御机制：传输加密 + 来源验证 + 客户端加固（三层）

### 第一层：加密 DNS 传输（防止中间人篡改）

明文 DNS（UDP 53）可被中间人篡改。采用加密协议保护通信链路：

- **DNS over TLS（DoT）**：通过 TLS 隧道传输 DNS（端口 853），防止窃听和篡改。
- **DNS over HTTPS（DoH）**：通过 HTTPS（端口 443）传输，复用 TLS 加密，兼具强穿透性。
- **配置方式**：操作系统或应用配置为使用支持 DoT/DoH 的解析器（如 `1.1.1.1`、`9.9.9.9`），或自建内部加密 DNS 服务。

加密传输可抵御路径篡改，但无法验证响应内容的权威性，需结合下一层。

### 第二层：DNSSEC 验证（防止伪造响应）

DNSSEC 通过数字签名链为解析结果提供来源验证：

- **签名验证**：权威 DNS 为资源记录签发签名，递归解析器验证整条签名链（从根到域），确保响应确来自授权服务器且未被修改。
- **启用验证**：递归解析器（如 BIND 带 DNSSEC 验证、Unbound）和客户端库需开启验证功能。验证失败的响应应丢弃，拒绝回退明文。
- **注意**：DNSSEC 依赖根信任链且不加密查询内容，但能有效阻止伪造响应；若目标域未部署签名，请求方可策略性要求拒绝无签名响应。

### 第三层：可信递归解析器与缓存策略（控制解析源头）

选择或自建可信解析器，并合理管理缓存：

- **可信源**：使用企业级内部递归服务器或高信誉公共解析器（`1.1.1.1`、`9.9.9.9`），避免使用来源不明或运营商默认 DNS。
- **缓存管理**：设置合理 TTL 上限，定期清理缓存，降低已污染条目的驻留时间。
- **Hosts 加固**：系统 Hosts 文件设为只读并定期校验完整性，防止恶意篡改。

## 纵深防御（辅助层）

- **多源验证**：对关键域名同时向多个独立 DNS 查询，比对结果；不一致则告警并拒绝使用。
- **流量监控**：部署网络监控，检测异常 DNS 行为（如高频 NXDOMAIN、指向已知恶意 IP），配合威胁情报快速发现劫持。
- **应用层备用**：关键应用内置 IP 备份或启用证书 Pinning，当解析异常时通过备用路径或证书校验保障连接，注意 Pinning 的更新成本。

## 安全金律

- **加密和验证缺一不可**：所有查询须走 DoT/DoH 加密通道，同时启用 DNSSEC 验证，无签名或验证失败则拒绝。
- **解析器必须可控**：依赖可信递归解析器，不信任运营商或不可信公共 DNS。
- **缓存按需收紧**：TTL 不宜过长，定期清理缓存，防止污染长期生效。
- **客户端层层设防**：Hosts 只读、多源比对、应用层不单一依赖 DNS，将其作为潜在不可信输入处理。
