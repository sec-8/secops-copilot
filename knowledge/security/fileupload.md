# 文件上传漏洞防御

> 覆盖变体：Webshell 上传、畸形文件名绕过、MIME 类型伪造、扩展名双写/截断、二次渲染绕过。  
> 防御同源：内容校验 + 重命名存储 + 执行隔离 + 病毒扫描。

## 漏洞成因

文件上传漏洞源于应用程序允许用户上传文件，但未对文件内容、类型、存储路径和执行权限做充分校验。攻击者可通过上传包含恶意代码的脚本文件（如 PHP、JSP、ASPX 等），结合服务端对上传路径的访问，在服务器上远程执行任意命令。根本成因是“上传文件”与“执行文件”之间的权限边界未被有效隔离。

## 防御机制：内容校验 + 存储隔离 + 执行管控（三层）

### 第一层：文件内容校验（核心防线）

在文件存储前，对其真实类型和内容进行严格验证：

- **魔术字节校验**：读取文件头部签名（如 JPEG 的 `FF D8 FF`、PNG 的 `89 50 4E 47`），验证文件真实类型是否与扩展名声明一致，拒绝不匹配的上传。不可仅依赖 `Content-Type` 头或扩展名，两者均可伪造。
- **文件头尾完整性检查**：对图片类文件，可额外校验文件尾标识或尝试调用图像处理库（如 `ImageIO`）解析，确保文件结构完整且非伪装脚本。解析失败即拒绝。
- **内容安全扫描**：集成病毒扫描引擎（如 ClamAV）或 YARA 规则，检测已知恶意文件特征码，拦截含 Webshell 或恶意脚本的文件。

### 第二层：存储隔离与重命名（防止执行）

即使文件内容通过校验，存储方式必须消除其可执行性：

- **重命名存储**：使用服务端生成的随机 UUID 或时间戳 + 随机数作为文件名，完全抛弃用户原始文件名，阻断攻击者通过文件名猜测路径或利用路径遍历。
- **存储目录隔离**：将上传文件存储于 Web 根目录之外的独立目录，或配置 Web 服务器（如 Nginx、Apache）禁止该目录下的所有脚本执行权限（如 `location /uploads { location ~ .*\.(php|jsp|asp)$ { deny all; } }`）。
- **强制 Content-Disposition**：在响应文件时，强制使用 `Content-Disposition: attachment` 头触发下载，而非由浏览器直接渲染，进一步降低 HTML/JS 类文件在浏览器中的执行风险。

### 第三层：多维辅助校验（纵深增强）

- **扩展名白名单**：基于业务允许的格式（如 `jpg`、`png`、`pdf`），与 MIME 类型和魔术字节三者保持一致方可放行，取交集而非并集。
- **文件大小限制**：根据业务场景设置最大文件尺寸（如 10MB），防止超大文件耗尽存储或触发解压炸弹（Zip Bomb）。
- **文件名净化**：将原始文件名中的非字母数字字符（如 `../`、`\0` 空字节）移除或替换，防止路径穿越或截断攻击。

## 纵深防御（辅助层）

- **独立存储服务**：将用户上传文件托管至对象存储（如 AWS S3、阿里云 OSS）或独立文件服务，与应用服务器物理隔离，即使文件被上传，也无法直接访问应用上下文。
- **图片二次渲染**：对上传的图片进行重新编码（如缩放、格式转换），可自动抹除注入的恶意代码或冗余数据段，但需注意保持业务可用性。
- **访问 URL 不可预测**：对外提供的访问链接使用哈希化路径（如 `/files/{hash}/{filename}`），使攻击者无法遍历或猜解其他用户文件。
- **监控与告警**：实时监控上传目录的文件变化频率和类型分布，对异常批量上传或高危扩展名行为触发告警。

## 安全金律

- **扩展名和 Content-Type 不可信**：二者均可伪造，必须以文件头（魔术字节）作为类型判断依据，且与扩展名一致方可放行。
- **存储与执行必须隔离**：上传目录应置于 Web 根目录外，或明确禁止脚本执行，杜绝通过 URL 直接访问并执行上传文件。
- **用户文件名不可用**：存储时强制重命名为随机字符串，彻底消除文件名带来的注入和遍历风险。
- **单一校验不足，多重叠加才有保障**：文件类型、扩展名、大小、内容扫描四项必须全部通过，任何一项失败即拒绝。
- **上传即隔离**：上传后的文件不应与应用代码同属一个可执行上下文，应视为不可信资源对待。
