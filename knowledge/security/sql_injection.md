# SQL 注入防御

> 覆盖变体：联合查询注入、布尔盲注、时间盲注、报错注入、堆叠查询注入。  
> 防御同源：参数化查询 + 输入校验 + 权限管控。

## 漏洞成因

SQL 注入源于应用程序将用户输入直接拼接到 SQL 查询字符串中，使数据库无法区分指令结构与数据，导致用户输入的恶意代码被当作 SQL 语法执行。动态拼接字符串（如 `"SELECT * FROM users WHERE id = " + userId`）是直接根源，任何依赖后端过滤的思路都治标不治本。

## 防御机制：代码层根治 + 数据库层兜底（三层）

### 第一层：参数化查询（PreparedStatement / 参数绑定）—— 根治方案

将 SQL 语句的结构与数据分离：先通过占位符（如 `?`）向数据库提交预编译的 SQL 骨架，数据库完成语法解析后，再将用户输入作为纯数据参数绑定。此时用户输入仅视为字段值，无论包含 `' OR '1'='1` 或 `; DROP TABLE`，都只作为普通字面量处理。

**适用范围**：所有传入查询条件、插入值、更新字段值的动态数据，必须无条件使用参数化。这是唯一能从语义上隔离数据和指令的方案，**转义只是次选，不可作为主要依赖**。

### 第二层：输入校验与标识符白名单

当涉及动态表名、列名、排序字段（`ORDER BY`）时，此类标识符无法使用占位符，须采取：

- **严格白名单**：将用户传入的标识符与预定义枚举列表（如允许排序字段：`["id", "name", "create_time"]`）精确匹配，不匹配则直接拒绝。
- **类型强制转换**：对整型参数（如 `page`、`size`）强制转换为数值类型后再使用，消除隐式注入风险。

**转义函数（如 `mysql_real_escape_string`）的定位**：仅作为无法使用参数化时的兜底临时措施，且需确保字符集正确设置。在架构设计上不应优先考虑转义。

### 第三层：最小权限数据库账号

应用程序数据库账号必须最小权限：

- 按操作分账号：只读业务用 `SELECT` 权限，写入业务用 `INSERT/UPDATE/DELETE` 权限，禁用 `root` 或 `admin`。
- 禁用高危权限：应用账号不应拥有 `DROP`、`ALTER`、`CREATE`、`FILE`、`EXECUTE` 等 DDL 或系统级权限，即使注入成功也无法删表或写 shell。
- 库表隔离：不同应用使用独立账号，避免一个漏洞影响全局。

## 纵深防御（辅助层）

在代码层根治之上，数据库层和运维层提供额外兜底：

- **关闭错误回显**：将所有数据库异常封装为通用错误码，前端仅显示“系统繁忙”，日志记录完整堆栈，防止攻击者通过报错反推表结构。
- **数据库防火墙**：部署 SQL 异常流量监控，实时拦截可疑查询模式，作为被动防御手段。
- **视图与存储过程限制**：若使用视图，只暴露必要列；存储过程调用时同样遵循参数化原则，不拼接用户输入。

## 安全金律

- **参数化是强制标准**：项目中任何 SQL 拼接行为均视为安全红线，代码评审时一票否决。所有动态数据必须使用 `PreparedStatement` 或等效 ORM 参数绑定。
- **标识符只能用白名单**：表名、列名、排序字段若来自用户，必须与固定枚举比对，不可直接拼入 SQL。
- **账号权限缩到业务最小**：线上账号只授予必需的 CRUD 权限，不授予结构变更和系统管理权限。
- **不以过滤替代参数化**：正则或 WAF 仅作辅助缓解，不能作为主体方案，因为编码、注释符、二次注入均可绕过过滤。
